## Часть 1. Что построено — одной картинкой

Представь маленькую фирму:

* **офис** (LAN) — компьютеры сотрудников `pc1`, `pc2`;
* **витрина** (DMZ) — сервер `dmz-srv` с сайтом, на который ходят люди из интернета;
* **охранник на входе** (`gw`) — единственная дверь между офисом, витриной и улицей (интернетом);
* **улица** (WAN) — интернет и «чужой» компьютер `lab-wan`.

```
                 улица (WAN): интернет + host-only 192.168.56.0/24
                        │                     │
                    wan0│10.0.2.15        ext0│192.168.56.10  ← «внешний адрес» фирмы
                   ┌────┴─────────────────────┴────┐
                   │   gw — маршрутизатор/охранник  │
                   └──────┬─────────────────┬──────┘
                    lan0  │192.168.10.1     │172.16.20.1  dmz0
             офис (LAN)   │                 │   витрина (DMZ)
       pc1 .189, pc2 .138 (по DHCP)      dmz-srv 172.16.20.10 (nginx)
```

Охранник умеет три вещи:

1. **Пропускать или не пропускать** (firewall) — по списку правил.
2. **Подменять обратный адрес на письмах из офиса** (SNAT) — чтобы снаружи видели только адрес фирмы.
3. **Перенаправлять посетителей, пришедших на адрес фирмы, к витрине** (DNAT).

И ещё он **раздаёт сотрудникам номера столов** (DHCP) и **подсказывает адреса** (DNS).

## Часть 2. Каждая машина

| Машина | Что делает | Как настроен адрес |
|---|---|---|
| **gw** | маршрутизатор: nftables (firewall + NAT), dnsmasq (DHCP + DNS для LAN) | статика (netplan), а `wan0` — DHCP от VirtualBox |
| **dmz-srv** | веб-сервер: Docker-контейнер nginx на 80 порту + SSH | статика 172.16.20.10, шлюз 172.16.20.1 |
| **pc1, pc2** | клиенты офиса | **DHCP** от gw (адрес, маска, шлюз, DNS) |
| **lab-wan** | «чужой» компьютер в интернете — только для проверок | статика 192.168.56.20, маршруты внутрь через gw |

Сети в VirtualBox:

| Адаптер VirtualBox | Что это | Кто подключён |
|---|---|---|
| **NAT** | выход в настоящий интернет через Windows | gw (`wan0`) |
| **Host-only** | сеть «Windows ↔ виртуалки» 192.168.56.0/24 | gw (`ext0`), lab-wan, сам Windows (.1) |
| **Внутренняя сеть `lan`** | виртуальный коммутатор офиса | gw (`lan0`), pc1, pc2 |
| **Внутренняя сеть `dmz`** | виртуальный коммутатор DMZ | gw (`dmz0`), dmz-srv |

Внутренние сети изолированы: из Windows туда не попасть иначе как через gw — как в настоящей фирме.

## Часть 3. Путь пакета — три истории

### История 1: pc1 открывает сайт в интернете (SNAT)

1. pc1 (192.168.10.189) хочет на ubuntu.com. Это не его сеть → отправляет пакет **шлюзу** 192.168.10.1 (шлюз он узнал по DHCP).
2. gw смотрит правила forward: «из LAN в WAN — можно» → пропускает.
3. На выходе через `wan0` правило **masquerade** подменяет адрес отправителя 192.168.10.189 → 10.0.2.15 (адрес gw). Запись об этом кладётся в **conntrack** (таблицу соединений).
4. Ответ приходит на 10.0.2.15. gw по conntrack понимает: «это ответ pc1», подменяет адрес назначения обратно на 192.168.10.189 и отдаёт pc1.

Зачем: адреса 192.168.x.x — частные, в интернете их не маршрутизируют. Наружу видно только адрес шлюза.

### История 2: посетитель открывает сайт фирмы (DNAT)

1. Windows (192.168.56.1) открывает `http://192.168.56.10` — это внешний адрес gw.
2. На входе в gw правило **DNAT** меняет адрес назначения: 192.168.56.10:80 → **172.16.20.10:80**. Сделано это *до* маршрутизации, поэтому дальше пакет идёт в DMZ.
3. Правило forward «пропускать к 172.16.20.10:80, если это DNAT» → пропуск.
4. nginx отвечает, ответ идёт через gw, conntrack меняет адрес отправителя обратно на 192.168.56.10. Посетитель думает, что сайт на самом gw.

### История 3: взломанный сервер DMZ пытается залезть в офис (запрет)

1. dmz-srv пытается `ssh 192.168.10.189` или `ping`.
2. В forward первое подходящее правило: «из `dmz0` в `lan0` — **drop**, и записать в журнал `nft-drop: dmz->lan`».
3. Пакет выброшен. pc1 о нём даже не узнает.

А как же тогда pc1 получает ответы от сайта в DMZ? Правило `ct state established,related accept`: **ответы** на соединения, которые начал pc1, пропускаются. Запрещено именно **начинать** соединения из DMZ.

## Часть 4. Firewall (файл `gateway/nftables.conf`) по-простому

nftables — встроенный в ядро Linux фильтр пакетов (наследник iptables). Пакет проходит через **цепочки**:

| Цепочка | Какие пакеты | Политика |
|---|---|---|
| `antispoof` (prerouting, раньше всех) | все входящие | отсеивает поддельные адреса |
| `input` | адресованные **самому gw** | **drop** — запрещено всё, что не разрешено |
| `forward` | идущие **через gw** из сети в сеть | **drop** |
| `output` | исходящие от самого gw | accept |
| `nat prerouting` | до маршрутизации | DNAT |
| `nat postrouting` | после маршрутизации | SNAT / masquerade |

Правила читаются **сверху вниз до первого совпадения**. Порядок в `forward`:

1. `ct state invalid` → drop (мусор, не относящийся ни к одному соединению);
2. `ct state established,related` → accept (ответы на уже разрешённое);
3. ICMP echo сверх лимита → drop (защита от ping-флуда);
4. **DMZ → LAN → лог + drop**;
5. то, что прошло DNAT к 172.16.20.10:80 → accept;
6. LAN → DMZ: tcp 22, 80 и ping → accept;
7. LAN → WAN → accept;
8. DMZ → интернет: DNS (53), HTTP (80), HTTPS (443) → accept;
9. всё остальное → лог `nft-drop: fwd` + drop (политика).

В `input` (к самому gw): из LAN можно DHCP, DNS, SSH, ping; из DMZ — только ping; из WAN — ничего,
кроме **учебного** SSH с адреса Windows 192.168.56.1 (правило помечено `LAB-EXCEPTION`).

Лог: все отброшенные пакеты пишутся в журнал ядра с префиксом `nft-drop:` и **лимитом** (10 в минуту), чтобы флуд не забил диск.

Посмотреть вживую:

```bash
ssh gw "sudo nft list ruleset"
```

```bash
ssh gw "sudo journalctl -k | grep nft-drop | tail"
```

## Часть 5. Остальные кусочки

| Что | Где | Зачем |
|---|---|---|
| `net.ipv4.ip_forward = 1` | `gateway/sysctl.conf` | без этого Linux **не пересылает** пакеты между сетевыми картами — gw не был бы маршрутизатором. Файл в `/etc/sysctl.d/` → действует после перезагрузки |
| `rp_filter = 1` (strict) | там же | защита от подделки адреса отправителя: пакет принимается, только если ответ на его адрес ушёл бы через ту же карту, откуда он пришёл |
| dnsmasq | `gateway/dnsmasq.conf` | DHCP: пул 192.168.10.100–200, выдаёт маску, шлюз .1, DNS .1. Слушает **только** `lan0` |
| netplan | `*/netplan.yaml` | настройка IP в Ubuntu. На gw интерфейсы опознаются по MAC и получают имена wan0/ext0/lan0/dmz0 |
| Docker + compose | `dmz/docker-compose.yml` | nginx в контейнере, порт 80, `restart: unless-stopped` — поднимается сам после перезагрузки |

| Откуда → куда | SSH | ICMP (ping) | HTTP | DHCP | DNS |
|---|---|---|---|---|---|
| LAN → DMZ | ✅ | ✅ | ✅ | — | — |
| LAN → интернет | ✅ | ✅ | ✅ | — | ✅ |
| LAN → gw | ✅ | ✅ | — | ✅ | ✅ |
| **DMZ → LAN** | ❌ | ❌ | ❌ | ❌ | ❌ |
| DMZ → интернет | ❌ | ❌ | ✅ (+HTTPS) | — | ✅ |
| DMZ → gw | ❌ | ✅ | — | ❌ | ❌ |
| WAN → DMZ | ❌ | ❌ | ✅ только через DNAT | — | ❌ |

каждой зоне открыто только то, что ей реально нужно.**

## Часть 7. Вопросы преподавателя и ответы

**Что такое DMZ?**
Отдельный сегмент сети для серверов, доступных из интернета. Он отделён и от интернета, и от внутренней сети. Если сервер в DMZ взломают, атакующий не попадёт во внутреннюю сеть.

**Почему DMZ → LAN запрещено, а LAN → DMZ можно?**
Сервер в DMZ — самая атакуемая машина, ей не доверяем. Сотрудники LAN — доверенные, им можно пользоваться сервисами DMZ. Ответы сервера при этом проходят благодаря conntrack (`established`).

**Как ответ из DMZ доходит до LAN, если DMZ → LAN запрещено?**
Правило `ct state established,related accept` стоит раньше запрета. Ответ относится к соединению, которое начал pc1, — это `established`. Запрещены только **новые** соединения из DMZ.

**Что такое conntrack?**
Таблица соединений в ядре. Для каждого пакета известно его состояние: `new`, `established`, `related`, `invalid`. Это делает firewall stateful. Ещё conntrack помнит NAT-подмены, чтобы делать обратную трансляцию ответов.

**Чем SNAT отличается от DNAT?**
SNAT меняет адрес **отправителя** (на выходе, postrouting) — чтобы внутренние машины выходили в интернет под адресом шлюза. DNAT меняет адрес **получателя** (на входе, prerouting) — чтобы пришедшее на внешний адрес отправить на внутренний сервер.

**Почему masquerade, а не snat?**
masquerade сам берёт текущий адрес выходного интерфейса. У `wan0` адрес выдаётся по DHCP и может поменяться.

**Что такое hairpin NAT?**
Ситуация, когда клиент изнутри обращается к **внешнему** адресу своего же сервера. У нас: pc1 → 192.168.56.10:80. DNAT-правило не привязано к входному интерфейсу, поэтому срабатывает и для LAN. Если клиент в той же сети, что и сервер (dmz-srv → свой внешний адрес), нужен ещё masquerade, иначе ответ пойдёт напрямую мимо gw. Это правило тоже есть.

**Почему policy drop?**
Принцип «запрещено всё, что не разрешено явно» (default deny). Забытое правило = закрытый доступ, а не дыра.

**Зачем `ct state invalid drop`?**
Пакеты, не относящиеся ни к одному соединению (например, сканирование с флагами ACK/FIN без SYN), отбрасываются сразу.

**Почему DHCP только на LAN?**
В DMZ серверы со статикой — DHCP там не нужен. На WAN свой DHCP-сервер мог бы раздавать адреса чужим (rogue DHCP). dnsmasq слушает только `lan0`, и firewall принимает udp/67 только с `lan0`.

**Почему у сервера и роутера статика, а у клиентов DHCP?**
Адрес сервера и шлюза должен быть всегда один и тот же — на него ссылаются DNAT, маршруты, клиенты. Клиентов много, руками настраивать неудобно — DHCP выдаёт всё сам.

**Что выдаёт DHCP клиенту?**
IP из пула .100–.200, маску /24, шлюз 192.168.10.1, DNS 192.168.10.1, домен lab.local, срок аренды 12 часов. Посмотреть выданное: `ssh gw "cat /var/lib/misc/dnsmasq.leases"`.

**Почему разные диапазоны у LAN и DMZ?**
Так требует задание, и иначе маршрутизатор не смог бы различать сети. LAN — 192.168.10.0/24, DMZ — 172.16.20.0/24, оба из частных диапазонов RFC 1918.

**Что разрешено DMZ в интернет и почему?**
Только DNS, HTTP, HTTPS — чтобы сервер мог ставить обновления (apt) и скачивать образ (docker pull). Взломанный сервер не сможет открыть SSH или произвольный порт наружу.

**Зачем rate limit на ICMP?**
Защита от ping-флуда: больше 10 пакетов в секунду к gw (20 транзитом) — отбрасываются.

**Что такое anti-spoofing и как сделан?**
Защита от подделки адреса отправителя. Два слоя: `rp_filter=1` в ядре (strict reverse path) и цепочка `antispoof` в nftables: из LAN принимаются только адреса LAN, из DMZ — только DMZ, из WAN не может прийти внутренний адрес.

**Зачем логирование и почему с лимитом?**
Видеть атаки и ошибки конфигурации (`journalctl -k | grep nft-drop`). Лимит — чтобы флуд не забил журнал и диск.

**Что будет после перезагрузки gw?**
Всё восстановится само: правила в `/etc/nftables.conf` + сервис `nftables` включён, sysctl в `/etc/sysctl.d/`, адреса в netplan, dnsmasq включён. Тест `check.sh --reboot-gw` это проверяет.

**Где SSH-доступ к gw и почему с Windows — исключение?**
Из LAN — штатно (администрирование). С Windows по host-only — учебное послабление (`LAB-EXCEPTION`), только с адреса 192.168.56.1, иначе нельзя управлять лабой. В реальной сети — убрать и ходить через VPN/бастион.

**Почему nginx в Docker?**
Так требует задание. Плюсы: изоляция сервиса, лёгкое обновление (сменить образ), `restart: unless-stopped` поднимает контейнер после перезагрузки.

**Зачем машина lab-wan?**
С Windows нет маршрута во внутренние сети, поэтому проверка «снаружи нельзя в DMZ» с Windows ничего не доказывает. У lab-wan маршруты в LAN/DMZ ведут через gw, как у атакующего в сети провайдера. Тест показывает: пускают только на 80 через DNAT, всё остальное — drop.

**Что бы ты поменял для продакшена?**
Убрать SSH из WAN и учебные пароли; HTTPS вместо HTTP; ограничить output gw; обновления DMZ через прокси/зеркало; логи в SIEM; резервный маршрутизатор; IDS. Подробно — раздел 11 отчёта.

**Почему ping 8.8.8.8 иногда SKIP в тесте?**
На Windows включён VPN, он не пропускает ICMP даже с самого Windows. VirtualBox NAT пингует от имени Windows, поэтому из VM ping наружу тоже не проходит. С выключенным VPN проверено: ping 8.8.8.8 из pc1 — PASS, весь тест 43 PASS / 0 FAIL (`docs/check-output-novpn.txt`). Выход в интернет при включённом VPN проверяется TCP и HTTPS.

## Часть 8. Демонстрация за 2 минуты

Все команды — в Git Bash из папки `lab-dmz`.

1. Сайт с Windows: открыть в браузере `http://192.168.56.10` → «DMZ web server (dmz-srv)».
2. LAN видит DMZ:

   ```bash
   ssh pc1 "curl -s http://172.16.20.10"
   ```

3. DMZ не видит LAN. В первом окне следить за журналом:

   ```bash
   ssh gw "sudo journalctl -k -f | grep nft-drop"
   ```

   Во втором окне пробовать с сервера:

   ```bash
   ssh dmz-srv "ping -c3 192.168.10.189"
   ```

   Ping не проходит, в первом окне появляется `nft-drop: dmz->lan`.
4. Весь тест одной командой:

   ```bash
   bash tests/check.sh
   ```
